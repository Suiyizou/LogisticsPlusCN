# 追踪任务发布流程设计

更新日期：2026-11-04。本文保留最初的架构审阅，并补充本轮已经实现的代码与接口。实现完成不等于线上部署完成；生产部署与真实船司查询验收另行记录。

## 本轮已经实现

- 网站新增独立的持久任务发布流程。Excel 仍在浏览器识别，识别明细与原始审核行保存为服务器草稿；用户可修改、排除问题行，保存并审核后明确发布。没有把文件读取操作直接变成查询任务。
- `PublishedShipmentTaskService` 负责草稿、版本校验、发布、列表、取消和失败行重试；`PublishedShipmentTaskRepository` 使用 V6 迁移新增的任务、明细和历史尝试表。草稿和发布输入持久化，不再依赖浏览器状态。
- 发布在数据库事务内锁定任务，核对 `expectedRevision`、当前任务所有者权限、客户归属及逐行校验结果；重复发布相同版本返回同一任务，已发布输入被冻结。
- `PublishedShipmentTaskWorker` 逐步派发、查询状态、读取结果和入库。执行键固定为 `taskId:row:rowIndex:run:runNo`；网络重试和重启复用该键以及已保存的本地 job ID。只有明确重试已确认失败的查询，才建立新的执行尝试。
- worker 每一步领取有期限的租约，回写时在任务行锁内核对租约令牌及执行序号。进程中断保留恢复状态，不作为用户取消；接管未释放的租约需要等待其过期。
- 完整 `tracking.v1` 结果先保存到明细，再在一个数据库事务中保存业务快照、绑定客户、处理客户可见性并标记明细成功。事务失败只重试入库；完成的明细不重复执行。晚到结果保留更新的业务快照，返回内容也与该快照一致。
- 本机离线保留等待状态并退避重试。人工验证、无数据及已确认的执行失败作为失败明细保留，由用户明确重试。已确认失败时，取不到诊断结果文件不能把失败任务永久退回等待。
- 停止任务立即取消尚未派发的明细；已派发的任务先与本地队列对账并请求停止。本机离线时保持停止处理中，不能提前宣称已停止本地 Chrome。

新增页面位于业务网站的 Excel 跟踪任务入口。当前页面按前 60 条候选记录生成审核草稿，历史列表显示最近 20 个任务；接口列表最大返回 50 个。`IMPORT` 模式保存业务提单并要求客户归属；`QUERY_ONLY` 明确标为只查询，任务结果会持久保留，但不创建业务提单或客户面板记录。手工跟踪行保存业务占位记录，不查询船司。

任务管理位于「运输跟踪 → 追踪任务 → 任务管理」，与「任务清单」并列。可通过 `/workspace/tracking/task-management?taskId=...` 打开指定批次。页面复用 `TaskNetwork`，按批次聚合全部明细，支持神经网络、森林、树形和状态四种布局。仅 `ADMIN` 和 `BUSINESS` 可进入，列表按登录人归属隔离。页面只读网站已保存的任务，不代理本机全局 `/jobs`，也不发起真实查单。

## 当前接口与状态

以下路径均以 `/api/business/shipment-batch-tasks` 为前缀，使用现有业务登录与权限控制。

| 接口 | 请求与行为 |
| --- | --- |
| `POST /drafts` | 现有批次字段 `sourceFileName/channel/items/customerId/publishToCustomer/mode`，可附 `sourceRows`；保存草稿，返回任务快照及逐行 `validationErrors`，不执行查询 |
| `PATCH /{taskId}/draft` | 同样的平铺草稿字段，另加 `expectedRevision`；成功后版本递增，版本冲突返回 409 |
| `POST /{taskId}/publish` | `{ "expectedRevision": 1 }`；校验并发布；相同已发布版本重复调用不生成第二次执行 |
| `GET ?limit=20` | 直接返回任务快照数组，当前按登录人所有权查询；不是 `{ tasks: [...] }` 包装对象 |
| `GET /management?limit=50` | 返回当前登录人拥有的轻量摘要数组，默认 20 条、最多 50 条，无 `items`、`sourceRows` 或 `payload`。V7 新增并回填摘要字段，选中批次后按需调用详情接口 |
| `GET /{taskId}` | 返回快照；已知任务 ID 可由所有者或管理员读取 |
| `POST /{taskId}/cancel` | 请求停止，返回当前任务快照 |
| `POST /{taskId}/retry` | `{ "rowNumbers": [0] }` 选择已失败明细；索引来自返回的 `rowIndex`，从 0 开始，不是 Excel `sourceRow`；空集合或不传请求体表示重试全部失败行 |

快照保留既有批量结果结构，并增加 `revision`、`publishedAt`、`sourceRows`、`validationErrors`；明细包含 `rowIndex`、`localJobId`、`attempts`、错误及重试时间。

任务状态为 `DRAFT / QUEUED / WAITING / RUNNING / STOPPING / COMPLETED / STOPPED`。明细状态为 `PENDING / WAITING / RUNNING / PERSISTING / SUCCEEDED / FAILED / MANUAL / CANCELLED`。`PERSISTING` 表示结果已取得、业务保存尚未完成；`COMPLETED` 表示本轮所有明细已经结束，仍须查看 `failed` 等计数，不能把它当成全部查询成功。

## 兼容范围与尚未迁移的部分

- 原有 `POST /api/business/shipment-batch-tasks` 仍保留即时批量执行，使用旧的内存批次服务。新发布流程使用 `published_` 开头的任务 ID；已有查询、刷新调用无需改成草稿流程。不能把新流程的持久恢复保证套用到所有历史批次。
- 自动刷新继续使用 `cp_tracking_refresh_jobs` 和统一追踪适配器。在本地队列模式下仍通过同一台执行端查询；本轮没有把自动刷新计划全部迁移为新发布任务，也没有补齐旧即时查询路径的派发幂等记录。
- 本轮保存的是解析后的服务器草稿及审核来源行，没有新增服务器 Excel 解析器或原始 Excel 文件归档服务。
- 传输仍为网站后端经已有隧道调用本地 `/jobs`，再轮询状态、取结果；没有实现桌面主动领取任务，也没有依赖回调完成业务入库。
- 自动化验证使用模拟桌面队列覆盖发布、丢失接收响应、离线、恢复、取消、入库回滚及明确重试；真实船司验收应单独控制范围，不能以发布测试为由执行整份 60 票文件。

## 结论与业务流程

用户提出的流程正确：**网站导入 Excel → 形成草稿 → 识别、校验、人工修正 → 明确发布执行任务 → 本地执行端查询 → 业务服务器保存结果 → 更新业务面板**。

网站负责业务任务、权限、归属和结果保存；本地电脑负责运行 Chrome 和返回官网查询数据。“本地接收待执行任务”不要求电脑主动拉取任务，现有服务器向本机队列提交的方式即可承载这一流程。

必须区分两种发布：

- **发布执行任务**：将审核过的草稿变为可派发的查询任务，发布之前不得查询船司。
- **发布给客户**：决定某个客户能否查看已保存的提单结果。现有 `publishToCustomer` 是这个含义，不能用作执行任务的发布标志。

## 实现前基线（历史审阅）

以下是新增持久发布服务之前的状态，用于解释设计动机；不代表上文新流程仍存在这些缺口。

| 环节 | 代码事实 | 与目标流程的差距 |
| --- | --- | --- |
| Excel 识别与审核 | `frontend/src/features/shipments/useShipmentBatchTracking.js` 的 `handleBatchTrackWorkbook` 在浏览器读取 Excel；存在预览、排除行、审核确认与重复提单检查 | 尚不是服务器持久草稿；刷新页面不能依靠数据库恢复草稿 |
| 创建批次 | `POST /api/business/shipment-batch-tasks` 调用 `ShipmentBatchTrackingService.start`，随后立即 `executor.execute(() -> run(task))` | 没有独立的草稿保存、修改、发布接口 |
| 网站批次状态 | `ShipmentBatchTrackingService` 用 `ConcurrentHashMap` 保存任务，终态保留 24 小时；前端只在 `localStorage` 记住任务 ID | 浏览器重开可继续查看仍在运行的后端任务，但后端重启会丢失批次状态 |
| 本地派发与取结果 | `LocalTrackingQueueClient` 向配置的本机服务地址 `POST /jobs`，轮询 `GET /jobs/{id}`，最后读取 `GET /jobs/{id}/result` | 当前是服务器主动调用本地 HTTP 队列，经部署配置的隧道连接；没有桌面领取网站任务的协议 |
| 本地队列恢复 | `D:/AI/shipping-tracking/scripts/serve-track.mjs` 保存 `job.json`、`result.json`；重启恢复未完成项；支持 `Idempotency-Key` | 网站客户端当前没有发送幂等键，也没有持久保存本地 `job_id`；接收成功后断网存在重复派发风险 |
| 结果保存 | `ShipmentTrackingService.persistAtomically` 保存业务提单与快照；普通导入随后绑定客户；前端完成后重新读取提单列表 | 已有正常完成路径，但缺少跨网站进程重启的任务与本地结果对账；`QUERY_ONLY` 不保存业务快照 |
| 回调 | 本地队列支持提交 `callback_url` 后单次 POST 结果，保存回调状态 | 当前网站桥接没有使用回调；本地实现也没有持久回调重试，不能假定结果必然通过回调送达 |
| 自动刷新 | `cp_tracking_refresh_jobs` 已保存按提单运行的刷新计划、租约与失败信息，`ShipmentAutoRefreshService` 调用统一追踪服务 | 该表不是导入草稿/发布批次表；不能据此宣称发布流程已经持久化 |

## 原始方案与后续设计约束

以下设计细节保留用于后续扩展。已经落地的具体接口和状态以上文为准；其中桌面领取、回调可靠投递及统一自动刷新执行记录仍属后续选择。

继续使用现有 **网站后端 → 隧道 → 本地 `/jobs`** 通道，增加网站任务持久层与后台派发器，无需同时引入桌面领取协议或消息中间件。

```mermaid
flowchart LR
  A[Excel 导入与识别] --> B[服务器保存草稿]
  B --> C[审核与修正]
  C -->|明确发布| D[数据库待派发任务]
  D -->|POST /jobs + 幂等键| E[本地持久队列]
  E --> F[Chrome 查询船司]
  F --> E
  E -->|服务器 GET 状态和结果| G[业务服务器校验并入库]
  G --> H[业务面板读取最新快照]
```

### 1. 草稿和发布

建议新增任务主表、任务明细表；记录创建人、客户、源文件/来源行、草稿版本、识别结果、校验问题、修正值、发布时间、执行状态及结果关联。需要保留原始 Excel 时一并保存文件引用；原始来源值与修正后的查询值分开保存。

第一步可复用现有前端 Excel 识别，上传规范化明细并在服务器重新校验；如果要求文件上传后在服务器识别，再补文件上传与解析接口。两种方案都必须先保存服务器草稿，页面中的预览状态不能充当任务记录。

建议接口：`POST /shipment-task-drafts` 创建、`PATCH /shipment-task-drafts/{id}` 修改、`POST /shipment-task-drafts/{id}/publish` 发布。发布必须检查权限、客户归属、支持的船司/查询类型、单号及草稿版本，在同一事务中冻结本次输入并标记可派发；重复点击返回同一个已发布任务。只靠前端禁用按钮不足以防重复。

尚有问题的行应先修正或明确排除；排除原因保留在草稿。发布后的输入不可静默修改；修改应形成新版本/新任务。客户可见性保持独立字段。

### 2. 派发、离线和恢复

为每个执行项持久保存 `dispatchKey`、请求摘要、`localJobId`、尝试序号、`nextAttemptAt`、错误与租约。第一版可沿用现有一票对应一个本地 job，避免改变当前结果映射器的一票校验契约。

- 发布后后台派发器读取数据库待办，不依赖浏览器保持打开。
- 每次逻辑执行使用固定幂等键，例如 `task:{taskId}:item:{itemId}:run:{runNo}`；网络重试和进程恢复继续用原键与原输入。
- 收到 HTTP 202 后保存 `localJobId`；如果响应丢失，重发原键可取回同一个本地任务，再继续轮询。
- 本机离线或隧道暂不可达时，保留“等待执行端”并退避重试。查询是否已被接收不确定时先对账，不直接创建另一任务。
- 网站重启恢复数据库未终结项；本机重启复用已有落盘恢复。两边恢复职责独立。
- 船司要求人工验证时显示“待人工处理”，不能不断重跑；用户明确重试、或已确认终态失败后允许的业务重试，才建立新的执行尝试。
- 用户主动取消与暂时失联应区分。现有客户端在请求异常时尝试取消本地 job，持久派发实现应改为先对账，并仅按明确取消策略发送取消请求。

建议界面状态为：`草稿 → 待执行（含等待执行端） → 执行中 → 结果待入库 → 完成 / 部分完成`，并保留 `待人工处理 / 失败 / 已取消`。数据库分别记录派发、执行、入库状态，避免“本地已完成”被误显示成“业务已保存”。任务总体进度由明细状态汇总。

### 3. 结果入库与面板更新

继续以 `GET /jobs/{id}/result` 为结果读取通道。SSE 可通知进度变化，但断线后必须重新读取状态；不能把 SSE 消息当成唯一结果来源。

官网事实以本地返回的 `tracking.v1` 数据为准；业务服务器校验 schema、job、船司与查询号对应关系，保留完整原始结果及来源，再经过现有 mapper 保存业务快照和任务关联。客户归属、可见性、人工业务备注仍由业务系统管理，不能由执行端返回值覆盖。

结果落库要支持同一执行结果重复接收而不产生重复业务记录。数据库提交成功后才标记“完成”；若入库失败，保留结果并重试入库，不再次查询船司。较旧执行结果不得覆盖更新的快照。网站面板读取业务接口，区分查询时间、入库状态和上次有效结果；新查询失败时保留上次有效快照并展示此次错误。

暂不要求回调。以后启用回调时，需要接收端幂等、身份校验及持久投递重试，同时保留查询接口用于对账；当前单次回调实现不满足这个可靠性要求。

### 4. 自动刷新与可选桌面领取

自动刷新继续使用现有持久计划和统一追踪通道；它是系统产生的新执行尝试，无需重新人工审核已经发布的合法提单。每次刷新仍需稳定执行 ID、幂等派发、结果关联和失败退避，不能另开一套云端浏览器或沿用旧子查询链。并发人工刷新与自动刷新要有同提单协调，避免旧结果回写覆盖新结果。

若未来希望去掉服务器访问本机的隧道，再将传输替换为桌面主动领取：服务器原子领取任务、桌面续租、回传结果、过期租约恢复。它是另一种传输选择，不是实现上述发布流程的前置条件，也不是现有代码行为。

## 原实施顺序与验收清单

1. 建任务主表和明细表，实现持久草稿、编辑、审核、幂等发布；此阶段不执行查询。
2. 接入持久派发器与现有本地队列，补幂等键、本地 job 关联、离线等待及重启对账。
3. 接入幂等结果入库和业务面板状态，完成失败、人工处理、取消和重新执行的语义。
4. 将自动刷新纳入相同的执行记录与结果关联，再按需要增加 SSE 进度通知。

至少验收：重复发布不重复执行；接收后丢失响应不重复执行；网站重启后继续跟踪；本机离线后上线可继续；本机重启保留已完成明细；结果入库失败仅重试入库；部分失败可逐项处理；过期结果不覆盖新快照。可先用本地假队列完成这些故障场景测试，再进行范围明确的真实查询验收。
