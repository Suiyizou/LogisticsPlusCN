# 智能装箱导入：原始工作簿读取工具

## 设计目的

让模型理解不同供应商的表格结构，同时由程序从原始单元格提取数值。模型不用重新抄写几十、几百条货物记录；也不再依赖为每个客户编写一套表头正则。

处理链路：

```text
原始 XLSX / XLS / CSV / TSV
  → 只读解析，保留坐标、类型、合并范围和公式缓存值
  → Agent 调用 inspect_workbook / read_sheet_range
  → Agent 返回列映射、数据区间、包装粒度、单位与控制合计地址
  → 程序逐包装读取原始数值，保留混装续行
  → 来源覆盖、身份、件数、重量、体积核对
  → 人工预览与必要确认 → 装箱货物表
```

DeepSeek 兼容的工具调用由服务端执行函数并回传结果。它不意味着聊天接口原生支持直接读取 Excel 文件。现有 LLM 地址、模型与密钥设置继续复用；所选模型/接口必须支持 function tool calling。

## 为什么原先会错

原来的浏览器解析器已读到完整表格，不只是缺少读取 Excel 的库。旧链路将表格平铺、按行分批识别、再套用通用字段覆盖和聚合，丢失了包装与产品之间的粒度关系。

装箱算法的 `quantity` 是最终搬运包装数，`weightKg` 是单个包装毛重。产品内件数量必须保存在 `packageInfo.innerCargo`，不能填到 `quantity` 中。

本次实物清单中，75 个包装有 104 条产品明细，其中 29 条是混装续行。原识别结果的 41 行 `quantity` 合计为 6,050，恰好等于每个包装首条产品的件数合计，遗漏续行的 875 件。它不是 41 个实体包装。

按照系统的真实计算口径，错误结果的 `SUM(quantity × weightKg)` 达 6,180,985 kg；简单相加得到的 39,549 kg 并不是装箱算法使用的总重。因此不能用“聚合时将每箱重量直接累加”修复，那会破坏合法的同规格多包装数据。

## 接口与职责

### 原文件任务

`POST /api/text-recognition/tasks/workbook`

- multipart 字段 `file`，可选 `languageHint`，默认 `auto`。
- 在 multipart 解析前执行既有内部上传身份校验。
- 工作簿证据进入既有任务持久化与异步处理流程，无数据库结构变更。
- `/capabilities` 返回 `workbookTools: true`、`workbookToolProtocol: workbook-evidence-v1`，引擎版本为 `excel-package-evidence-v7`。
- 文件智能模式要求该协议。旧服务端不支持时明确提示升级，不静默改走丢失结构的文本路径。
- 粘贴文本仍使用原文本接口，不声称具备原文件的坐标核对能力。

### 只读工具

| 工具               | 输入                       | 返回内容                                                 |
| ------------------ | -------------------------- | -------------------------------------------------------- |
| `inspect_workbook` | 空对象                     | 表名、大小、隐藏信息、合并范围数量、少量预览             |
| `read_sheet_range` | 精确 `sheet` 与 A1 `range` | 单元格坐标、原始值、显示值、类型、公式缓存与相交合并范围 |

优先上传原始 Excel。CSV 不包含 Excel 合并范围、公式和显示格式，工具不能恢复已在转换过程中丢失的信息。

不执行宏、公式计算、外部链接、文件内指令或任意代码。公式只读取工作簿已有缓存；如果缓存和来源合计不可靠，需要人工复核原文件。

当前边界为文件 16 MiB、32 张表、每表 20,000 行、256 列、合计 200,000 个单元格、证据 JSON 8 MiB。单次范围最多 200 行、30 列；对话最多 8 轮、24 次工具调用，并限制单次及累计字节数。超过限制明确失败，不返回伪装完整的截断结果。大文件应拆成完整出运单据。

这些是调用次数与大小预算。原 `/capabilities` 中的 `taskDeadlineSeconds` 仍属于旧文本批处理；新工具会话尚未设置独立的整体墙钟截止时间。供应商响应很慢或触发重试时，可能超过前端一次轮询窗口，需要稍后从任务历史查看。这一边界需要真实模型联调后继续评估。

### 映射计划

计划声明以下内容，不接收模型直接输出的货物数值数组：

- 表名、完整数据起止行；包号/唛头、产品名称/型号、内件数、包装数、包装尺寸与重量所在列。
- `quantityBasis`：每身份一个实体包装，或来源明确提供的包装数量列。
- `weightBasis`：单包装重量，或包装组总重量；长度与重量单位必须明确。
- 包装类型、不可堆叠、保持朝上等约束的来源列与标签映射；不能从产品名称猜测。
- 件数、包装数、毛重、净重、声明体积的控制合计单元格地址；没有就保留空值。
- 非货物工作表需要显式忽略理由，并先完整读取该表。

最终计划引用的数据区域及控制合计必须确实通过工具读取。程序还独立检查遗漏数据行、续行和非空工作表，拒绝只读取第一页或部分包装的计划。缺少可确认的外包装尺寸/毛重时阻止导入，不能拿内部产品尺寸代替托盘尺寸。

## 包装与追溯

- 单实体保留 `packageNo`、`marks`、`sourceSheet`、`sourceRows`，`quantity = 1`；不同实体不按品名合并。
- 混装明细放在 `packageInfo.innerCargo.lines`，保留各产品规格、内件数和来源行。
- 未提供内件数时保持未知，不伪装成零。来源提供内件控制合计而提取结果未知时不能通过核对。
- 来源明确的多包装组可保留 `quantity > 1`，使用 `source-package-group` 标识；不虚构逐箱身份，不跨来源聚合导致明细丢失。
- 普通无身份散货继续支持原聚合方式。
- 原始小数精度经过任务保存、清洗导出、前端审核和主货物表导入时均保留。
- 后端清洗 Excel 保留原有 13 列顺序，追加包身份、来源、内件、总毛重与 JSON 明细，附带 reconciliation 核对表。
- 每条包装元数据同时携带 `sourceReconciliation` 核对信封，CSV 也会保留。重新导入时恢复核对，不能通过只读取第一张货物表绕过缺包阻断或体积确认；快速导入遇到需复核的数据会转入人工核对页。

## 核对与人工处理

任务返回 `reconciliation`：来源口径、提取合计、声明合计、阻断项、警告项，以及 `matched / review-required / blocked` 状态。核对元数据存储于现有任务 JSON，不需要新 SQL。

包装身份冲突、遗漏、范围身份不清楚、必要字段缺失或数量/重量不守恒时阻止导入。源声明体积和尺寸计算体积不同则并列展示，保留原尺寸，并要求确认。编辑或重开任务会清除先前确认，避免旧确认放行新数据。

这不是模型正确性的数学证明。模型仍可能将含糊列映射错，或误判一张表的用途。来源没有独立控制合计时，界面保留可追溯明细供人工审核；不应宣称任意供应商文件均能无人值守准确导入。

## 本次验证

真实原始 `.xls` 只读解析和确定性执行得到：75 包、6,925 内件、74,575 kg 毛重、70,817 kg 净重、93.528148 m³ 尺寸体积。源表声明 96 m³，仅产生待确认警告。文件 SHA-256 前后相同。

最终验证：后端 `mvn -B package` 332 项全部通过；前端 634 项全部通过，含 33 项导入专项回归，类型检查、生产构建与质量门通过。真实组件浏览器验收覆盖三状态、中英文、1440/390px 共 12 种组合。结构化记录见 [验收证据](evidence/smart-import-2026-10-26.json)。

自动测试使用去标识的混装清单以及原生内存 XLS/XLSX、CSV/TSV；覆盖工具协议、读取覆盖、混装、包装组、单位、约束、持久化、导出及前端核对。模型 HTTP 响应使用模拟服务。真实原文件执行使用测试指定的坐标计划，**没有调用真实 DeepSeek，也不等价于线上模型识别准确率验收**。

上线前需使用已配置的真实模型完成一次端到端原文件上传，再检查结果、人工确认和装箱导入。Docker Engine 本轮不可用，未以旧部署验收记录代替本功能验证。
